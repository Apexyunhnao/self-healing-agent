# Local Service Self-Healing Agent — 项目计划（评审稿）

> 本文档自包含，请独立评审后给出：方案优缺点、遗漏的风险、改进建议。
> 背景：CS 应届生求职作品集项目（AI Agent 方向），此前基于翻墙代理的"自愈"方案因法律风险已废弃，本方案换为**本地服务自愈**。

## 1. 一句话

一个运行在本机的自愈 Agent：持续监控关键服务（RAG 知识库、聊天网关），发现故障后由 LLM 诊断根因、从白名单动作中选择修复策略，执行后由**确定性验证器**证明修复成功；失败自动回滚，无法自愈时升级人工。全程状态机驱动，评估用故障注入测试集。

## 2. 痛点（真实场景）

作者本机常年跑着多个必须保持在线/健康的服务：

| 服务 | 端口 | 现状 |
|---|---|---|
| RAG 知识库（FastAPI+ChromaDB） | 8000 | 挂了靠人发现、人重启，曾有多次崩溃经历 |
| Hermes 聊天网关（消息平台接入） | 动态 | 已有 watchdog 脚本，但只告警不自动修复 |
| 调试浏览器（AI 评审用） | 9224 | 挂了评审流程直接断 |

企业视角：生产服务不可用 = 直接损失（钱/用户/信任）。SRE 的核心诉求就是**自动发现→自动修复→证明修好→修不好就回滚或叫人来**。这正是运维岗位和 Agent 岗位都认的硬技能。

## 3. 核心架构：确定性层 + LLM 决策层分离

这是本项目区别于"监控脚本"的灵魂，也是面试重点。

```
┌─────────────────────────────────────────────────┐
│                  orchestrator（守护循环）          │
│  每 N 秒 tick → 状态机驱动                        │
└─────────────────────────────────────────────────┘
        │                    │                │
        ▼                    ▼                ▼
  ┌─────────┐          ┌──────────┐     ┌──────────┐
  │ 探针层   │          │ LLM 诊断  │     │ 验证器    │
  │ probe   │          │ diagnoser│     │ verifier │
  │ 确定性   │          │ 唯一 LLM │     │ 确定性    │
  │ HTTP/进程│          │ 决策节点  │     │ curl/DB  │
  │ /DB检查  │          └──────────┘     └──────────┘
  └─────────┘                │                 ▲
                             ▼                 │
                       ┌──────────┐            │
                       │ 执行器    │────────────┘
                       │ executor │  修复动作（白名单，幂等）
                       └──────────┘
```

**分层理由（面试话术）**：
- 探针和验证器**必须确定性**：`curl -s -o /dev/null -w "%{http_code}"` 返回 204，比 LLM 说"应该好了"可信。修复要可证明，不能自吹。
- LLM 只用在**诊断环节**：探针能检测"挂了"，但说不清"为什么挂、该重启还是该清僵尸进程还是该回滚配置"。规则写不完所有 case，LLM 读探针数据+最近日志做根因分析、从**动作白名单**里选修复策略。
- 执行器只执行白名单动作（重启/清理/回滚），LLM 不能自由发挥——**这是 Agent 安全边界**：LLM 决策、机器执行、验证器证明，三者互相制衡。

## 4. 状态机（v1）

```
healthy ──探针失败──▶ degraded ──连续失败/严重──▶ diagnosing
  ▲                      │                          │
  │                      │                          ▼
  │                    探针恢复                    repairing
  │                      │                          │
  └────recovered◀────verifying ◀────────────────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
        修复通过→healthy       修复失败
                                  ├─可回滚→回滚→重新验证
                                  └─不可回滚/第3次失败→escalated(人工)
```

规则：
- 同一故障连续 3 次修复失败 → **强制升级人工**，防死循环
- 每次修复动作幂等：重启前先查进程状态，已死不重复 kill
- 状态转移全程落结构化日志（JSON），可回放

## 5. 监控对象与故障类型（v1）

监控：RAG 知识库（8000）、Hermes Gateway、调试浏览器（9224）

故障类型：
1. 进程崩溃/被杀
2. 端口被占（重启会失败）
3. HTTP 无响应/5xx
4. DB 损坏（PRAGMA integrity_check fail / Chroma 索引异常）
5. 磁盘空间不足（日志占满）
6. 配置错误导致启动失败

修复动作白名单（全部幂等）：
- 重启服务（先查→杀→启，标准命令）
- 清理僵尸进程
- 回滚配置（变更前自动备份，失败恢复旧配置）
- 清理旧日志腾空间
- 升级人工（危险操作/重复失败）

## 6. 技术栈（待评审）

- Python 3.11+ 标准库为主
- 状态机：**手写**（状态有限且明确，不依赖框架，展示工程能力；比 LangGraph 轻）
- LLM 诊断：走 API（DeepSeek 等），prompt 里给探针数据+日志片段，输出结构化 JSON（根因/置信度/建议动作/理由）
- HTTP 探针/验证：httpx 或 urllib
- 出口：CLI（`selfheal status / run / verify`）+ FastAPI 健康面板（可选）
- 备选方案：用 LangGraph StateGraph 表达状态机（作者已学过 LangGraph，但本项目认为手写更合适——状态有限、需要的是确定性而非对话灵活性）

## 7. 评估体系（面试杀手锏）

**故障注入测试集**（这是和 demo 的分水岭）：
- ≥20 个故障场景，JSON 格式标注：故障类型 / 注入方式 / 预期状态转移路径 / 预期修复动作 / 预期验证方式
- 覆盖：kill 进程、占端口、改坏 DB、删配置、模拟磁盘满、无故障基线（测误报）
- 按 8:2 切 train/holdout（固定随机种子），开发只用 train，holdout 最终验收

**指标**：
- 检测率：注入故障被探针发现的比例
- 修复成功率：状态机最终回到 healthy 的比例
- MTTR：从注入到恢复的时长
- 误报率：无故障时误触发修复的比例
- 回滚正确率：该回滚的场景正确回滚的比例
- 升级人工正确率：不该自愈的没硬修、正确升级的比例

**报表**：run_eval.py 自动注入故障→记录完整状态转移轨迹→出指标报表+3 个失败案例分析

## 10. 面试叙事

三项目递进逻辑：RAG=嘴（只读）→ 客服=手（读写）→ 编排器=脑（路由）→ **自愈=稳（运维）**。
企业最缺的是"稳定、可排查、有方案"的能力，本项目展示：状态机设计、确定性验证 vs LLM 判断的边界、幂等、回滚、升级人工、评估驱动（故障注入）。都是面试官能连环追问的硬话题。

## 11. 已知风险 / 待评审问题

1. **LLM 诊断的必要性**：20 个故障场景规则能不能全写完？如果规则够用，LLM 就是多余的——评审请评估 LLM 诊断在什么场景下真的加分。
2. **手写状态机 vs LangGraph**：哪个对作品集更有利？（面试官可能问"为什么不用 LangGraph"）
3. **故障注入的安全**：在作者本机注入故障（kill 真实服务）有风险，如何隔离？（建议：测试模式用 mock 服务/副本端口，不用真实服务）
4. **监控对象太少**：只有 3 个服务，项目会不会太薄？
5. **命名与包装**：作品集项目名（Local Service Self-Healing Agent）是否够亮？
