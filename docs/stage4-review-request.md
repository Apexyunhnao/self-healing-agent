# 阶段 4 评审请求：自愈 Agent 评估结果 + LLM 增量结论

> 本文档自包含，请独立评审后给出：方案优缺点、指标可信度、遗漏风险、面试叙事建议。
> 背景：CS 应届生求职作品集项目（AI Agent 方向），"Local Service Self-Healing Agent"——本地服务自愈编排器。作者非科班、基础一般，面试要能讲清楚每个数字怎么来的。

## 1. 项目一句话

运行在本机的自愈编排器：确定性探针监控服务 → 规则/LLM 诊断根因 → 策略门校验 → 白名单动作修复 → 确定性验证器证明恢复；失败回滚/升级人工。全程手写状态机，故障注入测试集驱动评估。

灵魂原则：LLM 可以提出修复建议，但只有确定性策略允许执行，只有确定性验证器可以宣布恢复。

## 2. 架构（5 层）

```
Probe(确定性) → Diagnoser(Rule baseline + LLM 增强) → Policy Engine(策略门)
→ Executor(幂等白名单动作) → Verifier(确定性+多次采样) → Incident/Audit 记录
```

- 确定性层（探针/执行器/验证器/策略门/规则诊断器）零 LLM import
- LLM 只做诊断（DeepSeek API），pydantic 校验输出，无 key/坏输出自动降级 Rule
- 状态机 13 状态：连续 2 次探针失败→degraded、3 次→diagnosing、3 次修复失败→escalate、2 次升级→quarantine、cooldown、retry budget

## 3. 评估体系（面试杀手锏）

- 故障矩阵 30 场景（24 单一 + 5 mixed + 1 baseline），JSON 声明每个场景的注入方式/预期行为
- 开发集 24 / 盲评集 6（种子 42，盲评开发期不跑）
- 指标：检测率 / 修复成功率 / 正确处理率 / Unsafe Remediation Rate（必须 0）/ Verification Escape Rate（必须 0）/ 误报率（必须 0）/ MTTR / LLM Incremental Value
- 口径：修复成功=最终 healthy；正确处理=healthy 或 awaiting_human（升级人工）；Escape=判 recovered 但服务实际仍故障；Unsafe=执行了不该执行的动作

## 5. 关键决策（请重点评审）

1. **LLM 零增量 → v1 标为"可选增强"**：当前探针信息下，Rule 已覆盖所有场景判断（mixed 场景 LLM 也没拿到额外信息）。诚实结论：不硬吹 LLM 价值，README 写"评估证明当前架构下 LLM 无增量，v1 默认 Rule，LLM 为可选实验模块"。面试叙事："我做了 LLM vs Rule 的对照评估，数据说明当前探针粒度下 LLM 没有信息优势——这比硬塞 LLM 更诚实，也展示了评估驱动"。
2. **修复成功率 56.5% 低于"回到 healthy"目标**：7 个场景走升级人工（策略门拒绝低置信度重启/预算耗尽）——这是安全设计（不冒险），算"正确处理"但不算"修复成功"。口径：正确处理率 95.7%。
3. **port_occupy_04 missed**：本环境注入是 no-op（测试环境问题，不是系统缺陷），报表如实注明。
4. **http_500 修复语义调整**：restart 增加"清状态文件"语义（模拟真实世界重启清内存），使状态型故障可被 restart 修复；http_error 置信度 0.6→0.8。
