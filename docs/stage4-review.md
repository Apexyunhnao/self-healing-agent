三、“LLM 零增量 → 标为可选增强”是否成立？
结论本身：在限定条件下成立，但不能推广

你现在的结论如果写成下面这样，是站得住的：

在当前 24 个开发集场景、探针只提供健康状态、白名单动作只有 restart / clear state / port release 的条件下，LLM 相对 Rule 没有提升自动修复率或正确处理率。

但如果你说“当前架构下 LLM 无增量”，范围就太大了。

原因是：
你的探针信息可能只是“服务是否健康”。如果 Rule 已经覆盖了“端口占用 → 释放端口”“HTTP 500 → 重启”这类映射，LLM 当然没有额外信息。这不说明 LLM 没价值，只说明当前任务对 LLM 来说太简单。

如何让 LLM 产生真增量？

可以从四个方面改：

1. 给 LLM 更丰富的输入

不要只给探针健康状态，给：

最近 50 行服务日志；

错误堆栈；

进程状态；

端口监听详情；

最近配置变更；

CPU / 内存 / fd 指标；

依赖服务响应时间。

这样 LLM 可能识别出 Rule 无法覆盖的故障模式。

2. 增加规则未覆盖的故障场景

例如：

配置文件语法错误但服务能启动；

文件句柄泄漏导致偶发 500；

数据库连接池耗尽；

依赖服务变慢但探针仍 200；

权限部分错误导致写日志失败；

半开连接 / TIME_WAIT 堆积。

这些场景规则不容易写死，LLM 可能有增量。

3. 允许 LLM 发起“信息收集动作”

例如：

读取指定日志文件；

查看进程启动时间；

检查配置文件变更时间；

请求某个接口观察响应体。

这样 LLM 从“被动接收探针结果”变成“主动诊断”。

4. 扩大动作白名单

例如增加：

重载配置；

清理缓存；

回滚最近配置变更；

重启依赖服务；

调整连接池参数。

但每个动作仍要策略门校验参数范围。

我的建议

不要把 LLM 只作为 v1 的可选实验模块。
那样项目在 AI Agent 岗位上的竞争力会弱。

更好的叙事是：

v1 我用规则覆盖已知高频故障，并用 LLM 对照实验证明“规则够用”。
v1.5 / v2 我扩展了日志、指标输入和动作空间，在规则未覆盖的故障上，LLM 开始产生增量。
这个增量的来源不是模型本身，而是输入信息量和动作空间。

这样你既展示了诚实评估，又展示了 LLM Agent 的设计能力。

四、修复成功率 56.5% vs 正确处理率 95.7% 面试怎么讲？

建议用这个话术：

我的系统有两个关键指标：自动修复率和正确处理率。

自动修复率是 13/23，56.5%。这个数字看起来不高，但原因是策略门主动把 9 个场景升级人工了。比如端口占用涉及其他进程，自动释放可能误杀；配置损坏重启也没用。

正确处理率是 22/23，95.7%。意思是绝大多数故障都被系统正确响应了——要么安全修复，要么安全升级。

对我来说，自愈系统的目标不是“所有故障都自动修”，而是“不确定时不要乱动”。如果为了提高自动修复率而放开策略门，Unsafe 和 Escape 就可能上升。

然后补一句：

我这里有 9 个升级场景的具体原因，可以展开讲。

这样面试官会觉得你清楚知道每个数字的含义，而不是只背指标。

五、数字 / 口径漏洞

1. “7 个升级”与“22 - 13 = 9”不一致

这是最容易被抓住的。
建议立刻统一为：

检测到 22 个故障；

自动修复 13 个；

升级人工 9 个；

未检测 1 个。

2. Unsafe 分母 110 不清晰

面试官可能问：

这个 110 是执行次数还是建议次数？为什么 LLM 路径执行了 110 次动作，Rule 只有 26 次？

你需要能一句话解释清楚。

建议口径：

如果 110 是建议次数，就明确写“LLM 建议 110 次，策略门拒绝 X 次，执行 Y 次，其中不安全执行 0 次”；

如果 110 是执行次数，需要解释为什么 LLM 会执行更多动作，以及这是否影响效率。

3. MTTR 口径不清

如果只统计自动成功场景，要明确说。
如果包含升级人工，8～10 秒不可信。

4. 正常场景只有 1 个

误报率 0/1 太弱。
面试官可能说：“你只测了一个正常场景，凭什么说误报率必须为 0？”

回答方式：

当前测试集只有 1 个正常场景，所以统计上确实不够强。我的保障主要来自机制：探针连续多次失败才进入 degraded，策略门不允许对 healthy 服务执行动作。后续我会补更多正常场景。

5. Escape=0 可能只是“探针和验证器共享盲点”

如果验证器没有独立实现，面试官可能质疑：

你的验证器是不是就是探针再跑一遍？

你需要准备回答：

验证器是否使用不同检查方式；

是否做多次采样；

是否检查副作用，比如进程是否真的重启、端口是否真的释放。

六、遗漏风险

盲评集未跑
开发集 24 个场景可能已经过拟合。盲评集 6 个必须跑完，并公开同样表格。

注入有效性没有 precondition check
port_occupy_04 暴露了这个问题。建议每个注入场景执行前自动验证“故障是否真的生效”。

探针 / 验证器独立性未说明
这是 Escape=0 可信度的关键。

策略门拒绝日志缺失

七、面试叙事建议

建议按这个顺序讲：

1. 一句话定位

我做了一个本地服务自愈编排器，核心不是让 LLM 自动修复，而是让 LLM 在确定性边界内提建议，只有策略门和执行器能动手，只有验证器能宣布恢复。

2. 为什么做这个项目

我想验证一个观点：LLM 在运维自愈里到底有没有增量。所以我搭了一套规则 baseline，再拿 LLM 做对照。

3. 架构和安全原则

探针、策略门、执行器、验证器全部确定性，零 LLM import。LLM 只做诊断，输出还要过 pydantic 校验，坏输出自动降级 Rule。

4. 评估方法

我做了 30 个故障场景，开发集 24 个，盲评集 6 个。关键指标不是只看修复率，而是 Unsafe 和 Escape 必须为 0。

5. 诚实结论

在开发集上，LLM 相比 Rule 增量是 0。原因是当前探针信息太少，规则已经覆盖了所有场景判断。所以我 v1 默认 Rule，LLM 作为可选实验模块。这个结论不是失败，而是说明评估驱动。

6. 安全结果

自动修复率 56.5%，但正确处理率 95.7%。9 个场景是策略门主动升级人工，不是系统修不好。Unsafe 和 Escape 都是 0。

7. 后续计划

盲评集跑完；给 LLM 增加日志、指标输入；扩大动作白名单；在规则未覆盖场景上重新评估 LLM 增量。

23. 面试官很可能问你的 8 个问题
你最好提前准备。
Q1：为什么不用 LLM 直接决定执行哪个命令？
答：

因为执行属于高风险 side effect，所以让 LLM 负责推理，不负责授权。Policy Engine 只允许确定性白名单动作进入 Executor。

Q2：Verifier 为什么不能用 LLM？
答：

因为“是否恢复”是一个需要可重复、可审计的事实判断，不应该依赖概率模型。

Q3：56.5% 为什么这么低？
答：

因为系统优先安全，部分低置信度和预算耗尽场景主动升级人工，因此自动恢复率和正确处理率是两个不同指标。

Q4：为什么 LLM 没提升？
答：

当前探针暴露的信息已经足够让 Rule 分类这些故障，所以 LLM 没有额外信息可利用。

Q5：那你为什么还保留 LLM？
答：

为未来 richer telemetry 和 unknown/OOD fault 做诊断增强预留，但当前默认关闭，因为实验没有证明它的收益能覆盖延迟和成本。

Q6：Unsafe 0 怎么证明？
答：

当前测试集中所有实际执行动作都经过 Policy Gate，另外通过非法 action、越界参数和 schema-valid 但 policy-forbidden action 做负向测试。

Q7：Escape 0 怎么证明？
答：

Recovered 判断和独立外部健康检查做交叉验证，而不是只依赖 Agent 内部状态。

Q8：你的测试集会不会 overfit？
答：

开发集和盲评集分离，开发期不运行盲评集；冻结实现后统一运行盲评集，并把测试注入配置外置。

这 8 个问题能答稳，你的项目就已经相当像一个成熟的 Agent Infrastructure 项目了。
