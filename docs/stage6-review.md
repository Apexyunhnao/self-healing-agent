② 修复率 59.1% vs 正确处理率 100%

这是最容易被击穿的地方。

修复 13/22 = 59.1%，说明 22 个故障里只成功自动修复了 13 个。

正确处理 22/22 = 100%，意思是剩下 9 个没修复的也算“正确处理”。

面试官一定会问：“没修复也算正确处理？那你这个自愈 agent 的价值是什么？”

你需要提前定义清楚：

正确处理 = 检测正确 + 动作安全 + 无 escape / unsafe / 误报，即使未自动修复，只要安全升级或标记人工介入，也算正确处理。

修复率 = 成功自动修复 / 需要修复的故障。

但如果 9 个未修复的故障只是“检测到然后告警”，那这个项目的自愈能力其实很弱。你需要给出故障分类：哪些能自动修，哪些只能告警，哪些需要人工。否则面试官会认为你在用“正确处理率 100%”掩盖修复率低的问题。

3. interview-prep 可能被击穿的问题

19 个问题里，以下几个大概率会被追问击穿：

Q：为什么修复率只有 59.1%？

如果回答“复杂故障难以自动修复”，面试官会继续问：

“哪些故障复杂？为什么难？”

“你的 agent 如何判断什么时候该放弃自动修复？”

“剩下的 41% 是怎么处理的？人工介入？还是只告警？”

需要准备故障分类表：可自动修复（如端口占用、进程崩溃）、不可自动修复（如配置错误、依赖缺失）、安全边界内不修复（如可能丢数据）。否则一问就穿。

Q：正确处理率 100% 和修复率 59.1% 的区别？

如果解释不清楚，面试官会认为你在玩文字游戏。
必须用具体例子说明：比如“端口占用故障，检测正确，执行了安全重启，修复成功；配置错误故障，检测正确，但没有自动修改配置，而是标记人工介入，因此修复失败但正确处理”。

Q：你这个项目和脚本 / 告警系统有什么区别？

这是最危险的问题。
如果你的回答只强调“检测率高”，面试官会直接判定“这就是个 if-else 规则引擎，不是 Agent”。
必须讲出 Agent 的闭环：观察 → 诊断 → 规划 → 执行 → 验证 → 学习，强调状态机、安全护栏、回滚机制、可观测性。否则项目定位会崩塌。

Q：35 个场景是不是你对着写的？

开发集 29 个场景检测 100%，盲评只有 6 个。面试官会怀疑过拟合。
你需要坦诚：开发集用于迭代规则，盲评用于验证泛化，但样本量小。同时说明后续如何扩展场景（模糊测试、混沌工程、真实生产数据）。

Q：为什么不用 LLM？

如果回答“成本高、没提升”，面试官会问：“那你投 AI Agent 岗位，你的 Agent 智能在哪里？”
需要调整为：LLM 作为可插拔策略，当前确定性故障场景下规则更优，但架构已预留 LLM 接口，用于未知故障的根因假设生成。并且展示你做过 LLM 集成实验，证明你有能力，只是场景不需要。

十二、interview-prep 最容易被击穿的 6 类答案
没看到那 19 道原文，所以我不能逐题点名。但从这类项目的常见问题判断，下面 6 类回答尤其危险。
1. “为什么一定需要 LLM？”
如果回答：

“因为故障情况复杂，LLM 更灵活。”

很容易被一句：

“那为什么你的实验结果是 +0pp、-5pp、+7.8s？”

击穿。
正确方向应该是：

“我并不认为一定需要。实验结果证明当前场景中 LLM 没带来正收益，因此默认关闭。”


2. “为什么不是普通脚本？”
如果回答：

“因为 Agent 可以自主决策。”

会被立刻追问：

“你的决策规则是不是其实全写死了？”

更好的回答：

“对于已知故障，确定性规则负责安全执行；Agent 的价值主要体现在 diagnosis、action selection、以及对未知组合状态的编排，而不是让 LLM 直接发 shell。”


3. “13/22 修复成功，你怎么好意思叫 self-healing？”
这是我认为非常可能被问到的问题。
必须提前准备一句：

“Self-healing 不是要求所有故障都强行修复，而是在允许自动修复的故障上完成闭环修复，在不允许安全修复的故障上正确拒绝，从而保证 Correct Handling，而不是盲目追求 Repair Rate。”

这句话很关键。

4. “为什么 Verifier 必须是确定性的？”
如果答案只有：

“AI 会产生幻觉。”

太浅。
面试官会继续问：

“那你为什么还允许 AI 做决策？”

更好的答案：

“LLM 可以承担非确定性的判断，但最终系统状态是否满足 invariants 必须由可重复的确定性检查决定，否则无法建立安全闭环。”

这个回答就很像 SRE / distributed systems 面试。

5. “你的测试集靠谱吗？”
如果回答：

“我测试了 35 个场景。”

很危险。
面试官马上：

“为什么 35？为什么这些场景？”

你需要回答：

fault taxonomy 怎么构建、为什么有 baseline、为什么有 blind set、为什么 invalid case 被剔除，以及哪些 case 是 holdout。

也就是说：

测试数量本身不重要，测试集合是怎么构造出来的更重要。


6. “你这个系统如果误判怎么办？”
这个问题应该成为整个 interview-prep 的王牌。
你的理想回答不是：

“尽量让模型准确。”

而是：

“我不把正确性全部押在模型准确率上，而是通过 action allowlist、参数约束、precondition、postcondition、verification 和 rollback，把模型误判的后果限制在安全边界内。”

这是非常好的 Agent 工程思路。

十三、tech_selection 最容易被挑战的点
技术选型最怕“因为大家都在用，所以我用了”。
对于这个项目，我认为以下 trade-off 最应该讲清楚：
Agent framework vs 自研 orchestrator

项目核心是可靠编排，不是 framework abstraction。

所以如果最终核心状态机、policy engine、verifier 都是自己实现的，这反而是优点。
